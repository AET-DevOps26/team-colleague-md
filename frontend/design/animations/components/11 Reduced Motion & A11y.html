§1 — The reduced-motion override normative

One @media (prefers-reduced-motion: reduce) block per C-file, located at the bottom of the file's CSS. Override target named animations + transitions; leave color-only transitions alone (those are considered safe). Don't scatter checks across keyframes — concentrate the override surface so audits only have to scan one block per file.

@media (prefers-reduced-motion: reduce) {
  /* Kill named animations */
  .toast.show       { animation: none; opacity: 1; }
  .skeleton         { animation: none; opacity: 0.7; }
  .like-btn.bumping { animation: none; }

  /* Kill non-color transforms; keep box-shadow as the affordance anchor */
  .avatar-btn:hover { transform: none; }
  .avatar-btn       { transition: box-shadow 160ms ease-out; }

  /* Strip transition: all to its safe subset */
  .composer         { transition: box-shadow 240ms ease-out; }
}

Color-only transitions (e.g. follow button hover, like icon color toggle) are not killed. The 120ms color swap is below the WCAG flicker threshold and is considered acceptable under reduced-motion. opacity changes are also kept — fade-in is the gentlest signal of state change.

§3 — Focus-visible ring normative

Every interactive element gets a 2px outline in var(--accent) with 2px outline-offset on :focus-visible only. Not :focus — mouse-clicking should not paint a ring; keyboard navigation and screen-reader navigation should. Tab through the row below to verify.

If a custom interactive element (e.g. a clickable card) needs a ring, scope the rule to [role="button"]:focus-visible or use a class — never broaden the global selector.

§5 — Live regions normative

State changes that aren't visible in the page's normal reading order need an aria-live region. polite for non-urgent updates (saved, copied, refreshed); assertive for blocking errors only. Don't double-announce — if a toast contains the same text as an inline message, only one needs the live attribute.

Polite
save, copy, refresh, count change, toast (default)
Assertive
form validation error, network failure, irreversible warning
Off
regions whose content is already announced via focus or a heading

In production, the visible toast box and the SR-only live region should share content via the same React component (<LiveRegion politeness="polite">) — the visible UI is one styling target, the live region is another, but the source string is single.

§6 — Motion-free state cues governance

Every animated state change must be conveyed by at least one non-motion signal too: color, position, or text. If the only difference between "saved" and "saving" is a spinner, reduced-motion users get no information. Three canonical alternates are documented below.

Rule of thumb: kill every animation in the demo, then read the screen as a static snapshot. If you can't tell which state each component is in, the static design is missing a cue — fix the static layer, not the motion layer.

§7 — Transparency & forced colors governance

Two less-discussed media queries that the React port must respect: prefers-reduced-transparency: reduce (Safari macOS only at the moment, but ratified in spec) collapses tinted/translucent surfaces to solid; forced-colors: active (Windows High Contrast) maps all colors to system tokens. The pill below changes shape under each.

Verified 3 followers Topic · Form & Hierarchy

Under forced-colors: active, set forced-color-adjust: none only on the elements you've explicitly remapped to system tokens — never globally. The default UA mapping handles 95% of the page; only chrome surfaces with color-mix() or alpha-channel backgrounds need the override.

§8 — Per-C-file audit checklist normative

Before flipping any C-file from Pending to Live in Plan.md, verify:

  • Single @media (prefers-reduced-motion: reduce) block at the bottom of the file's CSS (not scattered).
  • Every named @keyframes in the file is killed or replaced by the override block.
  • Every transition: all is either documented (with a comment explaining why "all") or replaced with named properties.
  • Every interactive element uses :focus-visible for the ring — never bare :focus.
  • Every state change has at least one non-motion cue (color, position, or text — see §6).
  • Live regions are scoped: polite for routine, assertive for errors, off for everything announced via focus.
  • If the C-file uses tinted/translucent surfaces, it provides a prefers-reduced-transparency fallback.
  • If the C-file uses non-token colors (alpha-channel, color-mix), it provides a forced-colors: active fallback.
  • Demo file's React-hint footer references useA11yMotion() or equivalent for any motion that needs JS coordination.

This checklist is the contract every C-file's Plan.md "Deviations" subsection should be auditable against.

React component hints

useA11yMotion()
Hook that returns { reduced: boolean, transparency: boolean, forcedColors: boolean }. Components consult this only when motion needs JS coordination (cancellable timers, FLIP). For pure CSS motions, prefer the @media block.
<FocusTrap>
Wraps modal/overlay content. Auto-focuses first focusable on mount, restores focus on unmount. Tab/Shift+Tab cycle within children. Esc handler optional via onEscape prop.
<LiveRegion>
Renders role="status" (polite) or role="alert" (assertive) with aria-atomic="true". Pairs with the visible toast/inline-error UI; both consume the same source string.
useFocusVisible()
Hook for components that need to know whether focus arrived via keyboard (so they can paint custom focus chrome). Most components shouldn't need this — :focus-visible in CSS is enough.
Tokens
--ring 2px var(--accent) · --ring-offset 2px · --ring-forced Highlight · --motion-safe color, opacity, box-shadow
